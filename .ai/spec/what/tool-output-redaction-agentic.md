# Agentic Tool-Output Redaction [PLANNED: OLS-3939]

Agentic-specific integration of the [shared tool-output redaction policy](tool-output-redaction.md). This is planned behavior, not a claim that the sandbox/operator/UI already implement it. Shared categories and signals are normative in the parent; this file owns the DeepAgents interception, per-run handoff and user-visible Agentic surfaces. See [tool-result inspection](tool-result-inspection.md) and [audit policy](audit-logging.md) for existing safety and source-evidence constraints.

## Sandbox boundary

1. Each implemented DeepAgents route (Anthropic, Vertex Gemini, native/custom OpenAI, Azure, and supported Bedrock/Vertex Anthropic) MUST apply the same effective default-on tool-output policy to model-visible tool successes and handled errors across MCP tools, shell/`oc`/`kubectl` output and skill-executed tool results. Use one route-independent middleware/wrapper before the inspection classifier and before the next main-model invocation, not one optional provider-specific event mapper. A trusted skill-source read exempt from injection inspection is **not** automatically exempt from redaction when its content is delivered to a model.
2. Apply existing SDK/tool output limits before the model-visible redaction boundary; inspect the **sanitized** effective result when inspection is enabled. This prevents a classifier request from leaking a raw secret to a provider. Reject inspection failures under the existing fail-closed policy, without publishing a partial normalized tool-result event or Result CR. Disabling inspection does not disable redaction. For tool-generated exceptions/errors that become model content, redact before model use or fail closed; never forward raw text on matcher or policy failure.
3. Compile the effective named-alternative matcher once per configuration revision during sandbox setup; reuse it for all tool results in that run and compute sanitized text, boolean flag and category counts in one substitution pass per result. Only actual tool-call IDs may be used for correlation. When the SDK exposes no ID, carry an explicit no-ID result rather than invent an identifier or attach the result to an ambiguous call.

## Evidence, events and UI

4. The sandbox MUST preserve the existing native source-span rule: a successful tool callback can record the complete raw result immediately at native completion, independently of subsequent inspection/redaction; content-enabled compliance copies can therefore contain raw sensitive data. This feature sanitizes **later model-facing and user-facing projections**, not those evidence records. On successful admission, normalized `ToolResultEvent` and any user-visible Result CR/result projection MUST contain only sanitized tool text and an associated per-reply `redacted` boolean and `redacted_count` integer. A rejected result emits no normalized result or misleading flag. Source audit and trace semantics are unchanged; access controls for raw evidence remain necessary.
5. The sandbox/agentic-operator MUST expose per-reply metadata to the Agentic UI through a **structured handoff**, correlated with actual call ID when available and the run/phase. A typed Result/status representation may retain records through completion; if live display is required, use a separate explicitly specified structured transport rather than parse prose logs. No assumed HTTP SSE exists between sandbox and UI today. The operator MUST NOT infer a badge by searching logs for placeholders. A record with no replacements has `redacted=false` and count zero, and the UI displays a clear accessible "Sensitive values redacted" indicator alongside each sanitized reply with `redacted=true`. Where the current UI has only a live pod-log viewer, it MUST NOT render raw tool payloads as user-visible replies; a badge cannot make raw content safe. If a transport cannot supply sanitized reply plus metadata atomically, it MUST NOT publish a partially safe tool reply.
6. Sanitize tool-derived values in any user-facing normalized event, Result CR, replay or other secondary projection before it becomes visible. Do not leak matched values through error strings, log-viewer details, copy or download actions. Raw approved native traces remain governed by the audit/collection specs; changing them requires a separate decision. If an AgenticRun has several tool calls, indicators are per actual reply, not a single vague run-wide safety badge.

## Operator configuration, logging and tests

7. The Classic `OLSConfig.toolOutputRedaction` effective policy MUST reach the Agentic sandbox via a validated operator handoff. `lightspeed-operator` owns the user-facing CRD field; `lightspeed-agentic-operator` owns the sandbox configuration delivery and typed UI-result handoff. Absent config is enabled with built-in defaults; an explicit disablement is observable. Incompatible or invalid rules MUST stop admission/setup with a safe reason rather than result in silent policy divergence. No MCP Gateway or RHOAI dependency is required.
8. Emit one metadata-only record per redacted result after interception, with tool name/correlation (validated and bounded), status, category names and match counts, never input, matched values or hashes. No per-result redaction record for no matches. A safe startup/revision state record and explicit-disable warning follow the parent policy; no raw tool content in new developer logs. A proposed `gen_ai.tool.pii_redacted` attribute is not treated as standard until validated against the deployed OTel schema. Native execution spans retain their independently captured source content.
9. Offline conformance MUST run the parent corpus and combined ConfigMap example against every supported DeepAgents route, including tool errors, offloaded reads, inspection on/off, concurrent calls, missing/ambiguous call IDs, matcher failure, replay and user-facing metadata. Verify no raw values reach either classifier or main model, normalized result or UI, and verify raw native source spans remain independently intact. Test that records and UI indicators cannot be inferred from unsanitized pod logs, that no fabricated call IDs appear, and that Result/status handoff retains per-reply rather than run-wide metadata. Live provider tests, when available, are separate evidence and must not be claimed by this document.
