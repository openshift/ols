# Agentic Run Termination

Product contract for stopping one `AgenticRun` and for hard-stopping sandbox workloads during cluster-wide suspension. Per-run cancellation spans the agentic operator and console; global suspension is initiated through `AgenticOLSConfig`. The two entry points share one teardown contract but retain distinct terminal outcomes.

Jira tracking: OLS-3298 (per-run cancellation epic), OLS-4018 (global kill-switch sandbox termination), OLS-4131 (confirmed-teardown stopping contract), OLS-4132 (operator and parent spec), OLS-4134 (console). See `decisions/0040-agentic-run-termination.md` for the design decision.

## Behavioral Rules

### Per-Run Cancellation [PLANNED: OLS-4132]

1. **Cancellation field**: `AgenticRun.spec.cancelled` MUST be an optional boolean with an effective default of `false`. Setting it to `true` requests permanent termination of that run.
2. **One-way transition**: CRD validation MUST allow `spec.cancelled` to change only from absent/`false` to `true`. Once true, it MUST NOT be cleared. The field is a third mutable-spec exception alongside `revisionFeedback` and (before first terminal transition only [PLANNED: OLS-4280]) `terminalTTL`; cancellation handling MUST run before generation-based revision handling.
3. **Authorization**: Any caller with effective Kubernetes RBAC permission to `patch` `agenticruns` in the run namespace MAY set `spec.cancelled=true`. The product MUST NOT add a cancellation-specific ClusterRole or inspect caller group names. Kubernetes RBAC cannot restrict `patch agenticruns` to this field alone.
4. **Valid run states**: A cancellation request MUST terminate any non-terminal run, including `Pending` and `Proposed` runs with no active sandbox. If the run was already terminal when cancellation is processed, its existing terminal outcome MUST remain unchanged.
5. **Reconcile precedence**: For a non-deleting run, the operator MUST evaluate global suspension before per-run cancellation, and cancellation before approval resolution, revision handling, terminal routing, or normal phase dispatch. A persisted cancellation request MUST prevent every later workflow stage from starting.
6. **Stopped outcome**: Per-run cancellation MUST NOT add a `Cancelled` phase. When the shared stop path confirms that the run's hub workload and access and, for a spoke run, its spoke access are removed within the deadline in rule 7, the operator MUST set the phase-relevant workflow condition to `False`, reason `CancelledByUser`, and message `Run stopped by user`, so the existing phase derivation yields `Failed`:

   | Phase when the stop is accepted | Condition set to `False` |
   |---|---|
   | `Pending`, `Analyzing` | `Analyzed` |
   | `Proposed`, `Executing` | `Executed` |
   | `Verifying` | `Verified` |
   | `Escalating` | `Escalated` |

   In the same status update, the operator MUST set `Stopping=False/TeardownComplete` and clear every `status.steps.*.sandbox` reference. `spec.cancelled` remains `true` for audit.
7. **Bounded outcome and cleanup**: Acceptance MUST block workflow progression immediately and start one fixed ten-second cleanup window. For cancellation, the deadline is ten seconds after the accepted `Stopping=True/CancelledByUser` condition's `lastTransitionTime`; retries, restarts, and spec-generation changes MUST NOT extend it. If hub and spoke teardown is still unconfirmed at that deadline, the operator MUST set the phase-relevant workflow condition to `False` with reason `CancellationFailed`, set `Stopping=False/TeardownFailed`, and retain the unconfirmed sandbox references in one status update. The run is then terminal `Failed`; its recorded failure condition and `Failed` phase MUST NOT change. Cleanup MUST continue on requeues and watch events; when a later pass confirms removal, it MUST set `Stopping=False/TeardownComplete` and clear the references in the same status update without changing the failure condition or phase. Global suspension uses the same stop path and its existing ten-second window from the persisted activation time: confirmation records `EmergencyStopped=True/SystemSuspended`, `Stopping=False/TeardownComplete`, and cleared references; deadline failure records the phase-relevant `False/EmergencyStopFailed` condition and `Stopping=False/TeardownFailed`, retains references, and continues cleanup. A later confirmed pass sets `Stopping=False/TeardownComplete` and clears references in one update without changing `EmergencyStopFailed` or the `Failed` phase. A run with no workload or access confirms on the first pass.
8. **Transition races**: Once `spec.cancelled=true` is accepted for a non-terminal run, it MUST also stop a next-stage sandbox created during an informer or reconcile race. No approval, Result CR, or revision observed afterward may resume or advance the run.
9. **Result integrity**: The operator MUST NOT synthesize an `AnalysisResult`, `ExecutionResult`, `VerificationResult`, or `EscalationResult` for cancellation. Existing Result CRs remain unchanged. A Result CR published after a stop request remains available for audit but MUST NOT advance the run or alter its stopped outcome.

### Global Suspension [PLANNED: OLS-4132]

10. **Existing control and bounded global outcome**: `AgenticOLSConfig.spec.suspended=true` remains the cluster-wide kill switch and MUST block new runs at admission and new workflow stages immediately. A current-generation `Suspended=True` condition with nonzero `lastTransitionTime` defines the activation. If `spec.suspended=true` has no current activation condition, the run controller MUST block and requeue without inventing a deadline. Before cleanup, it MUST persist `Stopping=True/SystemSuspended` with the activation timestamp and optimistic locking. The fixed cleanup window is ten seconds from that persisted activation time; retries, restarts, reason changes, and later run generations MUST NOT extend it. Confirmed hub and spoke teardown records `EmergencyStopped=True/SystemSuspended`, completes `Stopping=False/TeardownComplete`, and clears sandbox references in one status update. If teardown is unconfirmed at the deadline, the run MUST record the phase-relevant `False/EmergencyStopFailed` condition and `Stopping=False/TeardownFailed`, retain unconfirmed references, and continue cleanup. A later confirmed pass MUST set `Stopping=False/TeardownComplete` and clear references in one update without changing `EmergencyStopFailed` or the `Failed` phase.
11. **Global precedence**: For a non-terminal run, global suspension MUST be evaluated before per-run cancellation. If both signals are pending, suspension wins; it also takes over a run in `Stopping=True/CancelledByUser` when no outcome is recorded. `spec.cancelled` remains `true` for audit. Once `Stopping=True/SystemSuspended` is accepted, the source and activation timestamp MUST NOT be changed: later `spec.cancelled=true` MUST NOT convert it to cancellation, even if suspension is resumed or the config is deleted. A terminal outcome already recorded remains unchanged (rule 12).
12. **Terminal history**: Global suspension MUST NOT rewrite a run that was already terminal before suspension was processed, including a run already recorded as `Failed / CancelledByUser`. The global workload sweep still applies to active managed sandboxes associated with terminal runs.
13. **Sweep scope**: Suspension MUST hard-stop every active operator-managed sandbox workload, not only workloads referenced by non-terminal AgenticRun status. The sweep MUST include active workloads associated with terminal runs and leaked or orphaned workloads whose run status reference is absent. Already-completed Pods need not be deleted because they cannot perform further actions.

### Shared Hard-Stop and Cleanup Contract [PLANNED: OLS-4132]

14. **Access revocation and workload termination**: Both stop sources MUST use one run-controller stop path parameterized by source (`suspension` or `cancellation`). The path MUST attempt every applicable cleanup operation even when one operation fails: remove sandbox ServiceAccounts from reader bindings, delete execution RBAC, delete bare Pods with zero grace, delete SandboxClaims, and hard-delete active backing Pods where claim deletion alone is asynchronous. Hub confirmation MUST use the confirmed `CleanupSuspension` report. For a run with `spec.targetCluster`, the run controller MUST use the spoke client from `spokeAccessForRun` to delete and confirm absent, through authoritative `Get` reads, every run-owned spoke access object: per-step ServiceAccounts; per-run reader ClusterRoleBindings; execution Roles and RoleBindings in every namespace recorded in the run's `rbac-namespaces` annotation; and the execution ClusterRole and ClusterRoleBinding. The operator MUST maintain `rbac-namespaces` as a union across executions and MUST NOT drop a namespace. The write-ahead persistence ordering for that inventory is specified in rule 16. `Get` `NotFound` means removed; any other error, including unreachable spoke, missing kubeconfig, or forbidden access, is unconfirmed. The standing spoke credential has `get`/`delete` but not `list`; no spoke list permission or hub credential change is required. Only the run controller MAY perform spoke I/O; the config controller MUST NOT read spokes.
14a. **Run Stopping condition**: Both stop paths MUST expose teardown progress through the run-level `Stopping` condition in `status.conditions`. Cancellation acceptance sets `Stopping=True` with reason `CancelledByUser` in the same reconcile that first blocks progression; suspension acceptance sets `Stopping=True` with reason `SystemSuspended` and the persisted activation timestamp. Acceptance MUST block synchronous and asynchronous workflow progression. On confirmed teardown, the operator MUST set `Stopping=False/TeardownComplete` in the same status update as the confirmed outcome. At the applicable deadline, it MUST set `Stopping=False/TeardownFailed` in the same status update as the failed outcome. `TeardownFailed` is not permanent: when a later pass confirms cleanup, the operator MUST set `Stopping=False/TeardownComplete` and clear sandbox references in the same update, without changing the phase-relevant failure condition or `Failed` phase. The deadline and final outcomes are defined in rules 6, 7, and 10.
15. **No cooperative delay**: The operator MUST NOT wait for sandbox acknowledgement, Result CR publication, or normal Pod termination grace before hard-stop. Durable run status, existing Result CRs, Kubernetes audit, and product audit storage are the evidence sources after termination.
16. **Dual discovery**: Dual discovery—run-status references plus managed labels/owner identity—applies to hub resources. Spoke access MUST use deterministic object names only, not label inventory or list calls: per-step ServiceAccounts; per-run reader ClusterRoleBindings; execution Roles/RoleBindings in every namespace in the run's `rbac-namespaces` annotation; and the execution ClusterRole/ClusterRoleBinding. The operator MUST maintain `rbac-namespaces` as a union across executions and MUST NOT drop a namespace. When an execution has namespace-scoped spoke RBAC, the operator MUST persist that union—including every namespace the execution will target—on the AgenticRun with an optimistic-lock update before creating the first spoke Role or RoleBinding. Creation of any namespace-scoped spoke RBAC MUST NOT begin until that write succeeds. A failed or conflicting annotation write MUST abort the sandbox creation without creating namespace-scoped spoke RBAC; a retry MUST re-read and persist the union again. This write-ahead ordering ensures a crash or partial create cannot leave access in a namespace absent from the inventory. For each named spoke object, delete it and confirm with authoritative `Get`: `NotFound` means removed; any other error (including unreachable spoke, missing kubeconfig, or forbidden access) is unconfirmed. The standing spoke credential has `get`/`delete` but not `list`; no spoke `list` permission or hub credential change is required.
17. **Idempotency**: Repeated teardown MUST be safe. Already-absent resources count as successfully removed. Duplicate run reconciliation and global sweeping MAY target the same resource without changing the outcome.
18. **Cleanup retries**: Run reconciliation and relevant resource watch events MUST continue cleanup from stop acceptance and after either successful or failed terminal outcome. A failed operation or still-present workload/access MUST cause another run-controller cleanup attempt. A recorded failure condition and `Failed` phase MUST NOT change after later cleanup. If a later pass confirms removal, it MUST set `Stopping=False/TeardownComplete` and clear sandbox references in the same status update; cleanup progress MUST NOT be suppressed by the recorded outcome.
19. **Sandbox reference as progress**: `status.steps.<step>.sandbox` MUST remain populated while the corresponding workload or associated hub/spoke access is unconfirmed. A confirmed outcome clears references in its outcome status update. A failed outcome retains unconfirmed references; a later confirmed cleanup MUST set `Stopping=False/TeardownComplete` and clear the references in the same update. The phase-relevant `CancellationFailed` or `EmergencyStopFailed` condition and `Failed` phase MUST NOT change. The console MAY use a remaining reference to display shutdown progress.
19a. **Deletion with unverified access**: When a stopped `AgenticRun` targeting a gone or unreachable spoke is deleted, the operator MUST retry sandbox and RBAC cleanup for the bounded finalizer-retry window (60 seconds). If access remains unverified after the window and the only failure is a degradeable spoke error, the run controller MAY release its RBAC-cleanup finalizer with a Warning Event so deletion completes. This degraded release MUST NOT run while `spec.suspended=true` and access remains unverified. While suspension is active, the operator MUST retain the finalizer: the deleting run is the durable cleanup obligation and the only holder of the `rbac-namespaces` inventory. The run controller—not the config controller—MUST continue retrying deterministic-name spoke access using that union. The config controller MUST treat the deleting run as unresolved while access remains unverified under rules 21 and 23, and MUST NOT infer resolution from its `deletionTimestamp`. A missing spoke kubeconfig is unconfirmed for the stop outcome; the existing deletion-specific policy MAY treat it as hard gone and release the finalizer immediately only when suspension is not active. An invalid kubeconfig or network failure retries for the window. A hub permission, API, or non-degradeable cleanup error MUST keep the finalizer. Releasing the finalizer MUST NOT be treated as `TeardownComplete` or rewrite the run's `Stopping` condition or recorded outcome. The config controller MUST NOT perform a spoke sweep and MUST derive resolution from recorded run state as specified in rule 23.
20. **Late creation**: A managed sandbox that appears after a cancellation or suspension pass MUST be re-discovered by its watch or the next sweep and hard-stopped. A cancellation field or active global suspension MUST prevent replacement sandbox creation.
20a. **Outcome finality**: Once a stopped outcome is recorded under rule 6 or rule 10, it is final. A late workflow completion, Result CR, approval, or revision feedback observed afterward MUST NOT overwrite the stopped outcome or restart workflow progression. The terminal-history protections in rules 4 and 12 are unchanged. [PLANNED: OLS-4131]
20b. **Status-write concurrency**: The operator SHOULD use resourceVersion-checked status patches and, on conflict, reread and re-evaluate before reapplying, so a stale workflow-completion write cannot undo stop progress or a recorded stopped outcome. This is a recommendation; the contract does not require a separate controller queue or a specific concurrency mechanism. [PLANNED: OLS-4131]

### Suspension Completion [PLANNED: OLS-4132]

21. **Stopping definition**: `AgenticOLSConfig` MUST remain `Suspended=True` with reason `Stopping` while any active managed hub workload/access remains or while any affected non-terminal `AgenticRun` has not recorded its terminal stop outcome. A run already terminal before suspension MUST retain its historical outcome; if the activation requires cleanup for that run, its stop cleanup is unresolved until all sandbox references are cleared AND either no `Stopping` condition is present or it is `Stopping=False/TeardownComplete`. A run whose `Stopping=True` condition is pending its outcome counts as unresolved; an unverified spoke MUST NOT leave a non-terminal run in `Stopping` beyond its run-level ten-second deadline. If a non-terminal run appears while suspended, the condition MUST return to `Stopping` until that run records its stop outcome. The config controller MUST apply that same resolution predicate: all sandbox references cleared AND either no `Stopping` condition or `Stopping=False/TeardownComplete`. `Stopping=True` or `Stopping=False/TeardownFailed` is unresolved even when references are cleared. A deleting run that retains its RBAC-cleanup finalizer under rule 19a remains unresolved while its access is unverified; `deletionTimestamp` alone MUST NOT resolve it.
22. **Stopping observability**: While the reason is `Stopping`, the `Suspended` condition message SHOULD report the remaining active hub-workload/access count and the number of runs still awaiting a stop outcome. A hub list, delete, or authoritative-read error MUST keep the reason `Stopping` and surface an actionable message or Event. When the activation completes with errors, the error outcome MUST identify the unresolved run/resources rather than leave a run in `Stopping` indefinitely.
23. **Activation completion**: The condition MAY transition to `Suspended=True`, reason `AdminActivated`, only after the operator confirms that managed hub resources and access are removed and every run affected by the activation is resolved under rule 21: each run that was non-terminal when suspension was accepted has a recorded stop outcome; an already-terminal run retains its historical outcome. The run controller alone performs spoke I/O. The config controller MUST NOT use `RemoteExecutionEvidence` or perform spoke reads to resolve runs; it MUST resolve each run only when all sandbox references are cleared AND either no `Stopping` condition is present or it is `Stopping=False/TeardownComplete`. A deleting run that retains its RBAC-cleanup finalizer under rule 19a is unresolved; the config controller MUST NOT treat its pending deletion as resolution. If the ten-second stop deadline expires with cleanup still unconfirmed, the run controller records the appropriate terminal failure outcome and the config controller MAY report `Suspended=True`, reason `AdminActivatedWithErrors`; `SafeToResume` MUST remain `False` while any affected run has `Stopping=True`, `Stopping=False/TeardownFailed`, or retained sandbox references, even when its hub references are already clear. If a later pass confirms cleanup, the run controller MUST set `Stopping=False/TeardownComplete` and clear references in one update; the phase-relevant `CancellationFailed` or `EmergencyStopFailed` condition and `Failed` phase remain unchanged. `SafeToResume` MAY then become `True` for the current generation under the rule 21 predicate, but the activation's `AdminActivatedWithErrors` outcome MUST remain unchanged. A reachable spoke whose resources are confirmed removed MUST NOT by itself force `AdminActivatedWithErrors`.
24. **Immediate blocking**: Reason `Stopping` does not weaken suspension. Admission blocking and reconcile guards MUST remain active from the moment `spec.suspended=true`, before teardown completion or status-condition writes.
25. **Safe resumption**: An attempt to set `AgenticOLSConfig.spec.suspended=false`, or to delete the config while it is suspended, MUST be rejected unless the current-generation `Suspended=True` condition has reason `AdminActivated` or `AdminActivatedWithErrors` AND current-generation `SafeToResume=True`. `AdminActivatedWithErrors` alone is not permission to resume. Rejection MUST also cover the window after `spec.suspended` becomes `true` but before the operator first records `Suspended`; an absent, `False`, or `Stopping` condition MUST NOT be treated as permission. A later cleanup confirmation MAY change `SafeToResume` to `True` without changing the recorded activation outcome.

### Console Behavior [PLANNED: OLS-4134]

26. **Stop control visibility**: The agentic console MUST show a danger-styled `Stop run` control only during active sandbox phases: `Analyzing`, `Executing`, `Verifying`, and `Escalating`. Direct API cancellation remains valid for every non-terminal phase under rule 4.
27. **Access review**: The console MUST call `useAccessReview` for `patch` on `agenticruns` in API group `agentic.openshift.io`, scoped to `run.metadata.namespace` (falling back to the run-watch namespace before the run loads). The effective permission controls whether the Stop control is shown or enabled. The console MUST NOT inspect groups or reuse the `patch agenticrunapprovals` approval check as a proxy. The API server remains authoritative for the patch.
28. **Confirmation**: Stopping requires confirmation that the action is irreversible. During `Executing`, the confirmation MUST warn that partial cluster changes may exist and require manual inspection.
29. **Mutation and errors**: Confirmation MUST send a JSON Patch `add` operation at `/spec/cancelled` with value `true` to that same namespaced AgenticRun. It changes no other field and succeeds whether `cancelled` is absent or already present; `spec` remains required. The console MUST NOT optimistically change phase; after a successful patch it waits for the operator to set the run's `Stopping` condition. A failed patch, including a stale-permission `403`, MUST leave the current phase visible and display the API error.
30. **Stopping and stopped presentation**: While the run's `Stopping` condition is `True`, the console MUST display `Stopping` prominently instead of the derived phase in list and detail views. After a confirmed cancellation outcome, the run MUST retain the `Failed` phase badge and display `Stopped by user`. If the effective failure condition reason is `CancellationFailed`, list and detail views MUST display `Stop failed`; this recorded outcome takes precedence over the pending-stop presentation even though `spec.cancelled` remains `true`. If a sandbox reference remains under rule 19, the detail view MUST also display `Sandbox shutdown in progress`; it MUST NOT present the failed stop as a clean stop. [PLANNED: OLS-4134]
31. **Global presentation**: When rule 11 applies, the console MUST show `Emergency stopped` after the `EmergencyStopped` outcome is recorded, not `Failed / Stopped by user`. While the run is `Stopping`, rule 30's `Stopping` presentation applies. The existing `EmergencyStopFailed` presentation remains unchanged.

## Integration Contracts

### AgenticRun API Addition [PLANNED: OLS-3298]

| Field | Type | Mutability | Meaning |
|---|---|---|---|
| `spec.cancelled` | optional boolean, effective default `false` | one-way absent/`false` → `true` | Permanently request termination of a non-terminal run |

`spec.cancelled` is intent. An accepted stop first sets the run-level `Stopping` condition (rule 14a); the observed outcome is the phase-relevant condition with `status=False`, `reason=CancelledByUser`, and `message=Run stopped by user`, recorded once teardown is confirmed.

### Outcome Precedence

For termination signals and existing terminal state:

1. A terminal outcome already processed before a new stop signal remains unchanged.
2. For a non-terminal run, global suspension is evaluated before cancellation. If both signals are pending, or if no outcome is recorded and the run is already `Stopping=True/CancelledByUser`, suspension wins and records its source-specific outcome; `spec.cancelled` remains true for audit.
3. Once `Stopping=True/SystemSuspended` is accepted, cancellation MUST NOT rewrite its reason or activation timestamp, even if suspension is resumed or the config is deleted.
4. Otherwise, `spec.cancelled=true` is evaluated before approval, revision, terminal routing, or phase dispatch. A persisted stop signal prevents all later workflow progression.
5. Once recorded, a stop outcome is final; late completions, Result CRs, approvals, revisions, and cleanup retries MUST NOT change it or restart the run.

## Required Test Coverage

### Agentic Operator

- CRD validation accepts absent/`false` to true and rejects true to false.
- Every non-terminal phase maps to the condition in rule 6, the `Stopping` condition is set when the stop is accepted, and no later phase starts.
- The stopped outcome is written only after teardown is confirmed in both sandbox modes (bare Pod and SandboxClaim), including RBAC removal; the `Stopping` condition completes in the same status update.
- A stale workflow-completion status write cannot undo stop progress or a recorded stopped outcome (resourceVersion conflict causes reread and re-evaluation).
- For each phase mapping in rule 6, test confirmed cancellation and the ten-second `CancellationFailed` outcome; assert the outcome condition, `Stopping` condition, and sandbox-reference changes are written together. Test that late cleanup sets `Stopping=False/TeardownComplete` and clears retained references in one update without changing the `CancellationFailed`/`EmergencyStopFailed` condition or `Failed` phase.
- Pending and Proposed runs can be cancelled through the API; with no sandbox workload or access present, the outcome follows without delay.
- Global suspension wins when both stop signals are pending; an existing terminal outcome is preserved.
- Bare Pods receive zero-grace deletion; SandboxClaims and active backing workloads are terminated.
- Label/owner discovery finds workloads with missing status references and active leaked/orphaned workloads.
- Cleanup errors requeue, status references remain until complete, and successful retry clears them.
- Late Result CRs and late sandbox creation cannot advance or restart a stopped run, and a late completion cannot overwrite a recorded stopped outcome.
- Test confirmed and unconfirmed spoke cleanup for both cancellation and suspension using deterministic names: per-step ServiceAccounts, per-run reader ClusterRoleBindings, execution Roles/RoleBindings across the `rbac-namespaces` union, and the execution ClusterRole/ClusterRoleBinding. Assert that the operator preserves the namespace union across executions, and that authoritative `Get` returning `NotFound` confirms removal while any other error (unreachable, missing kubeconfig, forbidden) is unconfirmed. Verify no spoke `list` call or hub credential change is required.
- Test that a reachable spoke whose named access objects are confirmed absent does not by itself force `AdminActivatedWithErrors`, and that the config controller resolves runs only when all references are cleared AND either no `Stopping` condition exists or `Stopping=False/TeardownComplete`; assert `Stopping=True` and `Stopping=False/TeardownFailed` remain unresolved even when references are clear. Resolution MUST NOT use `RemoteExecutionEvidence`.
- Test suspension precedence over pending cancellation, including takeover of `Stopping/CancelledByUser`, and prove that accepted `Stopping/SystemSuspended` is never converted to cancellation even after suspension is resumed or its config is deleted. Test that `AdminActivatedWithErrors` does not permit resumption while `SafeToResume=False`, and that later confirmed cleanup can set `SafeToResume=True` without changing the activation outcome.
- Persisting the `rbac-namespaces` union is write-before-create: when the annotation patch fails or conflicts, no namespace-scoped spoke Role/RoleBinding is created; after a successful patch, a partial create or crash leaves every target namespace in the inventory and deterministic-name cleanup checks it.
- Deleting a stopped run on a gone spoke with unverified access releases its RBAC finalizer after the bounded window only when suspension is not active; while suspension is active, the finalizer and namespace inventory remain, the deleting run counts as unresolved, `SafeToResume` stays false, and resumption is rejected. A hub cleanup error keeps the finalizer. After suspension ends, the bounded degraded release may proceed with a Warning Event.

### Agentic Console

- Stop appears only in active sandbox phases and uses namespaced `patch agenticruns` access review.
- A denied access review makes the Stop control unavailable; the console does not inspect user groups.
- Confirmation targets the reviewed namespace and sends JSON Patch `add` at `/spec/cancelled` with value `true`; errors do not optimistically change phase.
- Execution confirmation includes the partial-change warning.
- List and detail views show confirmed cancellation as `Failed` with `Stopped by user`, show `Stop failed` for `CancellationFailed`, and display `Sandbox shutdown in progress` when sandbox references remain.
- While the run's `Stopping` condition is true, list and detail views show `Stopping` instead of the derived phase label; `Stopped by user` or `Emergency stopped` appears only after the outcome is recorded.
- Simultaneous pending signals render the global `EmergencyStopped` outcome.

## Constraints

- `patch agenticruns` is resource-wide. Stop-only delegation is impossible with this boolean field and would require a separate API design.
- Cancellation does not establish which sandbox actions completed. Operators must inspect existing results, audit records, and cluster state before further remediation.
- Hard-stop safety takes precedence over retaining an active Pod for forensics. Durable audit systems, not a running sandbox, own post-incident evidence.
