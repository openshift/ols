# Classic Chat Tool-Output Redaction [PLANNED: OLS-3939]

Classic-specific integration of the [shared tool-output redaction policy](tool-output-redaction.md). This is planned behavior, not current service/console behavior. The parent policy defines categories, placeholders, defaults and match signals; this file defines where Classic applies them. The [inspection contract](tool-result-inspection.md), [query pipeline](query-pipeline.md), and existing service `what/tools.md` remain in force except where the planned user-facing raw-SSE change below explicitly supersedes the current rule 18n. Child specs must be aligned during delivery.

## Rule sets and lifecycle

1. Classic chat has **two independent effective rule sets**, even if they share matcher code. The existing administrator-configured `ols_config.query_filters` redacts prompts and attachments in the query pipeline; when omitted or empty it has no patterns. OLS-3939 MUST NOT automatically install tool-output defaults for prompts, change prompt filter ordering, or process an individual prompt through a new implicit tool-output policy. Separately, `OLSConfig.toolOutputRedaction` MUST supply default-on built-in tool rules plus validated administrator changes. Compile the effective tool matcher once per revision and reuse it for all MCP tool results; reuse the existing prompt redactor only if prompt behavior is preserved and payload-bearing debug logging is removed.
2. Execute external MCP tools and existing retries/approval logic normally. Apply existing model-facing size limits, then redact the effective success/error string and every effective offload preview/search/read result **before** the isolated injection classifier, main-model reinjection, or `<tool_data>` wrapping. Preserve the raw executor result separately only for the existing full-fidelity source audit boundary. Redaction is independent of the injection-inspection switch; if inspection is enabled, it classifies the sanitized effective text. Neither model receives the raw string.
3. Concurrent tool results form one inspection round under the [inspection contract](tool-result-inspection.md). No passing or rejected result from that round, and no redaction flag for it, may reach the user until all results pass; failure emits only the existing safe error. Redaction counts are computed per emitted result and associated with its actual `tool_call_id`, not with the round as a whole. Approval-denied synthetic messages do not falsely claim an external tool result was redacted. If matching fails, fail closed without forwarding the raw result.

## User-facing reply and signal

4. The existing `tool_result` SSE event MUST carry **sanitized** `content` instead of its current raw result. Add `redacted: boolean` and `redacted_count: integer` as per-reply metadata alongside the existing call ID/status and other metadata; do not invent a separate uncorrelated notification event. A reply with zero replacements carries `false` and `0`; if any delivered user-visible field had a replacement, `redacted` is true and the count includes each distinct source occurrence once. Avoid double counting when the same value is projected into text and structured fields.
5. The console MUST show the sanitized reply and an accessible visible "Sensitive values redacted" indicator only for `redacted=true`. Copy, download, expansion, tool cards, replay and transcript views MUST NOT expose the original tool result. The signal describes **that matching occurred**, not that all possible secrets were found. When redaction is explicitly disabled, `redacted=false` means no substitutions were made, not that the result is certified safe; any UI indication of disabled protection must be separate from the per-result flag.
6. Sanitize `structured_content` (including MCP Apps payloads), result references and any other user-visible projection that can carry tool values before serializing an SSE/response or persisting user-visible history/transcripts. Preserve safe structure and non-sensitive values. If a field cannot be sanitized without risking raw disclosure, omit it and provide a payload-free omission indication rather than include it verbatim. User-visible conversation history and replay use the same sanitized representation as SSE. Source audit records retain full-fidelity raw results under their separate policy; do not accidentally replace them with sanitized SSE content or send their raw representation to the console.
7. The live UI signal is bound to the reply event after inspection acceptance, not to early executor completion. The service MUST NOT stream a raw preview or an early redaction event while a concurrent round remains uninspected. For non-streaming requests the same sanitized user-visible result/metadata rule applies where results are exposed; it does not require inventing an SSE connection for that API.

## Configuration and observability

8. `lightspeed-operator` MUST reconcile `toolOutputRedaction` into the service configuration and hand the same effective policy to the Agentic configuration owner. Absent configuration uses built-in defaults; only an explicit opt-out disables matching. A bad pattern must fail configuration validation and cannot silently disable either runtime. Configuration reload recompiles once per revision, not per user query or tool call.
9. For a result with replacements, the service MUST record one metadata-only redaction record containing a bounded tool identifier, call correlation, result/error status, total count and category counts; no per-result redaction record for zero matches. It MAY annotate the existing tool span with a validated, documented boolean rather than invent an unsupported standard attribute. Configuration state and safe failure reporting follow the parent policy. Remove the current `Redactor` debug logs of configured filters and post-redaction input; those fields may contain secrets even when no rule matched.
